# v0.4 — `modelbox` skill: curated flowunit index

**Date:** 2026-05-06
**Status:** Approved (brainstorm)
**Predecessors:** v0.1 scaffold, v0.2 remote, v0.3 naming + experiment log.
**Successor:** v0.5 will use this skill for `app-builder` / `/package` / `/poc`.

## Goal

Give Claude a small, curated index of ModelBox flowunits — names, device options,
TOML config schema, ports, when-to-use guidance — so it can author ModelBox
graphs without reading the upstream C++ codebase. Implemented as a single skill
with progressive-disclosure references plus a reproducible generator.

This is a prerequisite for v0.5 (`app-builder` + `/ultralytics:package` +
`/ultralytics:poc`). It is also independently useful — anyone writing a
ModelBox `.toml` graph in Claude Code benefits.

## Audience

Claude itself (skill is model-invoked). Secondary audience: human developers
reading the references when they need to remember a flowunit's config keys.

v0.4 ships ~19 flowunit references — exactly the set needed for the v0.5 MVP
path on **two chip targets** (NVIDIA + TensorRT, Apple Silicon + CoreML). Path:
file/http source → decode → preprocess → infer → yolo postproc → draw →
encode/sink. Other flowunits (Ascend ACL, OpenVINO, MindSpore, Rockchip RKNN)
land in later versions when the corresponding chip targets do.

Apple Silicon was added to the v0.4 set after upstream merged first-class
support: `src/drivers/devices/apple_silicon/` device driver, `coreml_inference`
flowunit, and a `src/demo/apple_silicon_yolo/` reference pipeline. The demo
shape (file → demuxer → decoder → resize → coreml_inference → yolo26_post →
videotoolbox encoder) maps 1:1 to the NVIDIA pipeline shape — same DAG, swap
device + inference engine. Bringing both chips into v0.4 simultaneously costs
us only 3 extra reference files and a virtual_type matrix row.

## `SKILL.md` shape

Frontmatter:

```yaml
---
name: modelbox
description: Use when authoring or modifying a ModelBox graph (.toml), configuring a ModelBox flowunit, choosing the right flowunit for a step (video decode, inference, YOLO postprocess, drawing boxes, encoding output), or resolving "which flowunit handles X". Provides a curated index of flowunits used in YOLO + video pipelines, with TOML config schema, ports, device options, and known-good recipes.
---
```

Body sections (in order):

1. **When to use** — graph authoring, flowunit picking, resolving naming/config questions.
2. **Core mental model** — pipeline = directed graph of flowunits; each unit declares device + inputs + outputs; graph file is a `.toml`. Two-line refresher; defer to upstream docs for the rest.
3. **Catalog** — markdown table:

   ```markdown
   | Flowunit               | Devices       | Group     | Use for                                      | Reference |
   |------------------------|---------------|-----------|----------------------------------------------|-----------|
   | `inference`            | cuda, cpu     | Inference | Run any model; `virtual_type` picks engine   | references/inference.md |
   | `video_demuxer`        | cpu           | Input     | Split mp4/mkv container into elementary stream | references/video_demuxer.md |
   | `video_decoder`        | cuda, cpu     | Input     | Decode H.264/H.265 to frames (NV12/RGB)      | references/video_decoder.md |
   | `image_process`        | cuda, cpu     | Process   | Resize/letterbox/colorspace/layout convert   | references/image_process.md |
   | `normalize`            | cuda, cpu     | Process   | Per-channel normalize (mean/std)             | references/normalize.md |
   | `yolo26_post`          | cpu           | Postprocess | YOLO detect head → boxes (anchors, NMS)    | references/yolo26_post.md |
   | `yolo_seg_post`        | cpu           | Postprocess | YOLO segment head → masks                  | references/yolo_seg_post.md |
   | `yolo_pose_post`       | cpu           | Postprocess | YOLO pose head → keypoints                 | references/yolo_pose_post.md |
   | `yolo_track_post`      | cpu           | Postprocess | YOLO + tracker → tracked boxes              | references/yolo_track_post.md |
   | `draw_bbox`            | cpu           | Render    | Draw boxes/labels on frames                  | references/draw_bbox.md |
   | `video_encoder`        | cpu           | Output    | Frames → H.264 mp4                           | references/video_encoder.md |
   | `data_source_generator`| cpu           | Input     | File/dir source (replays paths into a stream) | references/data_source_generator.md |
   | `httpserver_async`     | cpu           | Input/Output | HTTP request/reply edges                  | references/httpserver_async.md |
   | `output_broker`        | cpu           | Output    | Send results to Kafka/RocketMQ/HTTP/file     | references/output_broker.md |
   | `meta_mapping`         | cpu           | Process   | Rename / project / drop fields between units | references/meta_mapping.md |
   | `mean`                 | cuda, cpu     | Process   | Per-channel mean subtract                    | references/mean.md |
   ```

4. **Virtual-type matrix** — which `virtual_type` for which chip:

   ```markdown
   | Chip                  | virtual_type | Common flowunit device | Inference flowunit  |
   |-----------------------|--------------|------------------------|---------------------|
   | NVIDIA GPU            | tensorrt     | cuda                   | `inference`         |
   | NVIDIA GPU            | torch        | cuda                   | `inference`         |
   | Apple Silicon (M-series) | coreml    | apple_silicon          | `coreml_inference`  |
   | Huawei Ascend         | acl          | ascend                 | `inference`         |
   | Huawei Ascend         | mindspore    | ascend                 | `inference`         |
   | Intel Arc/iGPU        | openvino     | intel_gpu              | `inference`         |
   | CPU fallback          | onnxruntime  | cpu                    | `inference`         |
   ```

5. **Known-good pipelines** — four canned recipes with the exact graph DSL skeletons:

   - **NVIDIA file → detect → annotate → file** (the v0.5 MVP shape on cuda + tensorrt).
   - **Apple Silicon file → detect → annotate → file** (same DAG, `device=apple_silicon` on the infer node, `virtual_type=coreml`, `encoder=h264_videotoolbox` on the video_encoder). Mirrors `src/demo/apple_silicon_yolo`.
   - **HTTP request → detect → JSON reply** (chip-agnostic; swap the infer node).
   - **RTSP → detect → output_broker** (chip-agnostic).

   Each recipe lists the flowunit chain and points to which references to read
   to fill in the configs. Approximate length: 30 lines per recipe. Recipes 1
   and 2 are byte-similar — the catalog calls out the three lines that change
   so users see the swap point clearly.

6. **Authoring gotchas** — collected pitfalls:
   - Device mismatches between adjacent units force a memory copy (acceptable but log it).
   - `inference`'s `entry` path is relative to the flowunit's own directory.
   - Image layout: cuda flowunits prefer NHWC for input, NV12 between decoder and processor.
   - `name=` field in `[base]` must match the flowunit directory name.
   - Graph wiring uses `:port_name` syntax; types must match (image, tensor, json, ...).

7. **Pointers** — link to upstream docs (`https://modelbox-ai.com/modelbox-book/`)
   and to the `yolo` skill for the YOLO-specific side of the pipeline.

## Reference file shape

Every `references/<flowunit>.md` has the SAME six sections, in this order:

```markdown
# `<flowunit_name>`

**Devices:** cuda, cpu
**Group:** Inference

## Purpose

One paragraph. What it does, when to reach for it.

## TOML config (`<flowunit>.toml`)

\`\`\`toml
[base]
name = "<your_unit_name>"
device = "cuda"
version = "1.0.0"
type = "inference"
virtual_type = "tensorrt"
entry = "./model.engine"

[config]
plugin = ""              # optional; "yolo" enables upsample layer for legacy yolov3

[input.input1]
name = "input"
type = "float"

[output.output1]
name = "output"
type = "float"
\`\`\`

## Ports

- **Inputs:** `input` (float tensor, NHWC float32 [1,640,640,3])
- **Outputs:** `output` (float tensor, model-defined shape)

## Config keys

| Key             | Required | Default   | Notes |
|-----------------|----------|-----------|-------|
| `entry`         | yes      | —         | Relative path to model file |
| `virtual_type`  | yes      | —         | tensorrt | torch | acl | mindspore | openvino |
| `device`        | yes      | —         | cuda | cpu | ascend | intel_gpu |
| `plugin`        | no       | ""        | "yolo" only for v3 upsample compat |

## Notes / gotchas

- A few short bullets.

## Upstream source

- `src/drivers/common/flowunit/inference/` (header schema)
- `examples/flowunit/infer/example.toml` (canonical example)
```

These six sections are the contract. The generator enforces all six exist; a
post-generation validator (a tiny markdown-section linter) checks each file.

## Generator script

`tools/build-modelbox-skill.py` is a Python 3 script with no third-party deps
beyond `tomli` (or `tomllib` on 3.11+).

```text
Usage:
    python3 tools/build-modelbox-skill.py \
        --modelbox-repo /path/to/modelbox \
        --commit <sha-or-tag> \
        --out skills/modelbox/

Inputs:
    - The upstream modelbox repo at the pinned commit.
    - A YAML allowlist `tools/modelbox-flowunits.yml` listing which flowunits
      to include this version, with hand-written "purpose" and "use for" text:

      flowunits:
        - name: inference
          group: Inference
          purpose: |
            Generic inference flowunit; loads a model file and runs it
            through the engine selected by `virtual_type`.
          use_for: Run any model; virtual_type picks engine
          example_toml: examples/flowunit/infer/example.toml
          source_dir: src/drivers/common/flowunit/inference
        - name: yolo26_post
          group: Postprocess
          purpose: …
          …

Outputs:
    - skills/modelbox/SKILL.md      (catalog + recipes + matrix; recipes/matrix are
                                     loaded from a hand-written tools/modelbox-skill-
                                     prelude.md and tools/modelbox-skill-recipes.md
                                     and stitched into the generated SKILL.md)
    - skills/modelbox/references/<flowunit>.md  (one per allowlist entry)

Behavior:
    - Reads each flowunit's example.toml when available; falls back to a
      hand-written default in the allowlist.
    - Emits the six-section reference layout. The TOML block is verbatim from
      upstream's example.toml.
    - Records the upstream commit and date in a footer of every generated file
      and at the bottom of SKILL.md.
    - Idempotent: re-running with the same inputs produces byte-identical output.
```

The generator is checked in. The generated files are also checked in (they are
the source of truth at runtime; the generator is for maintainers).

## Pinned upstream commit and CI auto-bumping

`tools/modelbox-flowunits.yml` carries:

```yaml
modelbox_repo: https://github.com/modelbox-ai/modelbox.git
modelbox_branch: master
modelbox_commit: <full sha at v0.4 cut>
modelbox_commit_date: 2026-05-06
```

The **GitHub Actions workflow `.github/workflows/modelbox-bump.yml`** runs on a
schedule (daily at 04:00 UTC) and on manual `workflow_dispatch`:

```text
1. Checkout this repo.
2. Clone https://github.com/modelbox-ai/modelbox.git --depth=200, resolve
   <new_sha> = HEAD of the configured branch.
3. If <new_sha> == modelbox_commit in the YAML → exit 0, no-op.
4. Otherwise:
   a. Run `python3 tools/build-modelbox-skill.py
        --modelbox-repo <clone>
        --commit <new_sha>
        --out skills/modelbox/`
      after first updating modelbox_commit/_date in the YAML in-memory.
   b. Run `python3 tools/test-modelbox-skill.py` (six-section linter, parity,
      TOML validity, footer pin record). On failure, the job fails — do not
      open a PR with broken output.
   c. Compute a human-readable diff summary:
        - Flowunits whose example.toml changed (config keys added/removed).
        - Flowunits in the allowlist whose source dir disappeared (rename or
          removal upstream — flag for manual attention).
        - New flowunits in upstream that are not in the allowlist (informational,
          not auto-added).
   d. Open or update a PR titled `chore(modelbox): bump pin to <short-sha>`
      against `main`, with:
        - The regenerated `skills/modelbox/**` files.
        - The bumped `tools/modelbox-flowunits.yml`.
        - The diff summary as the PR body.
        - Label `automation` and `modelbox-bump`.
      If a prior automated PR exists and is still open, force-push to its
      branch instead of opening a new one.
5. Maintainer reviews and merges (or closes if upstream changes are unwanted).
```

Failure modes the workflow handles:

- **Upstream removed a flowunit on the allowlist.** Generator emits a
  `MISSING:<name>` marker; linter fails; CI fails; no PR opened. The
  workflow's failure summary points the maintainer to the YAML for manual
  decision (rename, remove, or pin to an older commit).
- **Upstream renamed a flowunit.** Generator can't tell rename from delete;
  treats as missing; same path as above. Maintainer adds an alias entry to
  the YAML if needed.
- **Schema drift in example.toml.** Regenerated TOML differs; that's fine —
  the linter only checks structural validity, not byte equality. The diff
  surfaces it in the PR for review.

Manual override is always available: a maintainer can edit the YAML directly,
push to a branch, and the same generator/linter scripts run as CI. The PR-based
flow exists so drift is *surfaced* automatically, not so it's *applied*
automatically.

## Initial flowunit allowlist (v0.4 set, ~19)

Selected to cover the v0.5 MVP pipeline on **two chip targets** (NVIDIA + Apple
Silicon) for file → infer → annotate → file, with enough adjacent units to
cover the next two slices (HTTP shape, RTSP shape):

```
# Inference
inference                # generic; tensorrt/torch/onnxruntime/etc. via virtual_type
coreml_inference         # apple_silicon device, CoreML engine

# Sources
video_input              # file source (preferred for video)
data_source_generator    # generic file/dir source
httpserver_async         # HTTP request edge

# Video pipeline
video_demuxer
video_decoder
video_encoder            # h264_videotoolbox (macOS), h264_qsv (Linux), x264 (cpu)

# Image preprocessing
resize                   # standalone resize flowunit (cpu/ascend/rockchip variants)
image_process            # generic image ops (colorspace, layout)
normalize                # per-channel normalize
mean                     # per-channel mean subtract

# YOLO postprocessing
yolo26_post              # detect head
yolo_seg_post            # segment head
yolo_pose_post           # pose head
yolo_track_post          # tracker

# Output / utility
draw_bbox                # render boxes onto frames
output_broker            # Kafka/RocketMQ/HTTP/file sink
meta_mapping             # rename/project fields between units
```

Excluded for v0.4 (out of scope, will be added when their target chip is):

- All `intel_gpu/` flowunits (Arc target, v0.6).
- All `ascend/` flowunits (Ascend target, v0.6).
- All `rockchip/` flowunits (RKNN, later).
- C++ template flowunits (relevant only when authoring custom C++ units).

## Smoke tests

A small `tools/test-modelbox-skill.py` script verifies the generated artifacts
without invoking Claude:

1. **Section linter.** Every `references/*.md` has the six required headings
   in order; each has a non-empty body. `SKILL.md` has the seven required
   sections.
2. **Catalog ↔ references parity.** Every row in `SKILL.md`'s catalog
   references an existing `references/<name>.md`, and every reference file is
   referenced by exactly one catalog row.
3. **TOML validity.** The TOML block in each reference parses with `tomllib`.
4. **Pin record.** Every generated file's footer carries the pinned commit
   string from `tools/modelbox-flowunits.yml`.
5. **Frontmatter parses.** `SKILL.md`'s YAML frontmatter parses cleanly (same
   check `claude plugin validate` does).

`make modelbox-skill` runs the generator + tests. CI is out of scope for v0.4.

## Out of scope (v0.4)

- Flowunits for chips other than NVIDIA + Apple Silicon + CPU.
- A second skill that explains how to write a *custom* C++/Python flowunit.
  v0.4 is consumption-only; authoring is a different topic.
- Fully automatic merge of bump PRs. The CI workflow opens PRs; maintainers
  still review and merge.

## Risks

- **Upstream rename or schema drift.** Pinning the commit and storing the
  TOMLs verbatim absorbs all but the rarest schema breakage. The generator
  flags missing example.toml files loudly.
- **Allowlist coverage gaps.** v0.5's `app-builder` may discover a flowunit
  it needs but isn't in the allowlist. Cheap fix: add an entry to the YAML
  and rerun the generator.
- **Catalog rot.** Hand-written "purpose"/"use_for" text can lag upstream
  semantic changes. Mitigation: when bumping the pinned commit, generator
  diffs each flowunit's example.toml against the previous run and warns when
  configs change in non-trivial ways.
